# Задание 1. Анализ и планирование

### 1. Описание функциональности монолитного приложения

**Управление отоплением:**

- Пользователи могут получать список сенсоров, просматривать подробную информацию о сенсоре, добавлять, редактировать или удалять сенсоры.
- Система поддерживает запросы к REST API для получения или редактирования и информации о сенсорах.

**Мониторинг температуры:**

- Пользователи могут получать температуру, указывая необходимое помещение.
- Система поддерживает единственный запрос к REST API для получения температуры в интересующей комнате (запрос проектируется на внешнюю систему). 


### 2. Анализ архитектуры монолитного приложения

Текущее приложение прдставляет из себя монолит, написанный на языке Go с использованием фреймворка gin-gonic, в качестве базы данных используется PostgreSQL. Архитектурно приложение разбито на контроллеры, сервисы и хендлеры, репозиторий к базе данных. Явное разделение на модули по предметным областям отсутствует. 


### 3. Определение доменов и границы контекстов

В текущей архитектуре можно выделить следующие домены и контексты:

Домены
 - Система умного дома
 
Контексты
- Использование сенсоров
- Получение температуры из внешнего источника

### **4. Проблемы монолитного решения**

- Нет явно выделенных доменов
- Добавление новых типов устройств затрагивает всю систему;
- Потенциальные ошибки в ПО приведут к отказу всех подсистем;
- Нельзя масштабировать отдельные компоненты системы (например, управление температурой, в ситуации, когда датчиков становится много);

# Задание 4. Создание и документирование API

### 1. Тип API

Система будет использовать как REST API (для интеграции с WebUI и MobileApp), так и AsyncAPI для взаимодействия между микросервисами (через шину). Например, для добавления новых устройств в реестр или получения списка устройств в доме или комнате будет использоваться REST API. 

Для добавления устройства в отдельное хранилище микросервиса управления устройством (для возможности масштабирования БД), либо отправки телеметрии из микросервиса управления устройством в микросервис телеметрии будет использоваться AsyncAPI.

# **Задание 6. Разработка MVP**

- [каталог с приложениями](mvp)

Реализовано несколько приложений - 1) монолит с CRUD для сенсоров 2) микросервис для управления температурой 3) микросервис для управления воротами 4) микросервис для просмотра телеметрии. При добавлении сенсора в монолите, далее через шину (rabbitmq) отправляется соотвествующая push-команда, по которой каждый микросервис, отвечающий за свой тип устройств, создает собственную копию устройства. Управление устройствами (установка температуры, открытие \ закрытие ворот, отправка в шину телеметрии) происходит на стороне микросервиса. Добавление в БД данных по телеметрии и простое REST API для просмотра телеметрии по устройству реализованы так же в отдельном микросервисе.

БД на данный момент общая, но с возможностью выноса в отдельные базы таблиц, относящихся к своим микросервисами. 

Для тестирования в postman добавлен [mvp.postman_collection.json](mvp/mvp.postman_collection.json)
